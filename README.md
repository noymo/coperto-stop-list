# Coperto Stop List

Тестовое приложение для управления стоп-листом позиций меню. Менеджер может фильтровать меню по цеху
и статусу, ставить позицию в стоп, менять причину и срок стопа и возвращать позицию в продажу.

## Стек

- Nuxt 4, Vue 3, TypeScript
- Composition API и `<script setup lang="ts">`
- Pinia для состояния интерфейса
- TanStack Vue Query для серверного состояния
- VeeValidate и Zod для формы и валидации
- Tailwind CSS
- VueUse Motion
- ESLint и Prettier

## Запуск

Требования: Node.js 20+ и npm.


## Что реализовано

- список позиций меню с цехом, остатком, статусом, причиной и сроком стопа;
- фильтры по цеху и статусу;
- хранение фильтров в query-параметрах URL;
- корректная работа перезагрузки страницы и кнопок браузера «назад»/«вперёд»;
- состояния загрузки, ошибки и пустого результата;
- боковая панель постановки позиции в стоп и редактирования текущего стопа;
- срок «до конца смены» или конкретное время;
- проверка будущего времени, ограничения в 24 часа и шага в 15 минут;
- оптимистичное обновление списка;
- откат данных и уведомление при ошибке запроса;
- блокировка возврата в продажу при нулевом остатке;
- имитация задержки сервера и случайной ошибки мутации.

## Архитектура

```text
app/
  features/stop-list/
    model/                 фильтры, запросы и мутации
    ui/                    компоненты стоп-листа
  pages/                   страницы Nuxt
  plugins/                 подключение Vue Query
  shared/ui/               переиспользуемые UI-компоненты
  stores/                  состояние интерфейса
  utils/                   общие клиентские утилиты
server/
  api/menu-items/          Nitro API-обработчики
  utils/                   in-memory хранилище и имитация запросов
shared/
  constants/               общие константы и опции домена
  schemas/                 Zod-схемы
  types/                   общие TypeScript-типы
```

### Архитектурные решения

Страница связывает сценарии между собой, а запросы, мутации и работа с URL вынесены в model-слой фичи.
Серверное состояние хранится в TanStack Vue Query, тогда как Pinia отвечает только за панель и
уведомления. Доменные типы, справочники и Zod-схема находятся в `shared`, потому что используются и
клиентом, и Nitro API. UI-компоненты не знают об устройстве транспорта и получают данные через пропсы.

### Граница клиента и сервера

Код в `server/**` выполняется только на сервере: там находятся Nitro API-обработчики, in-memory
хранилище и имитация задержек и ошибок. Интерфейс и пользовательские сценарии находятся в `app/**`;
к серверным данным они обращаются через API и TanStack Vue Query. Общие доменные типы, константы и
Zod-схема лежат в `shared/**`, поэтому правила не дублируются между клиентом и сервером.

### Ключевые архитектурные решения

Серверные данные не дублируются в Pinia: кэш, инвалидация и оптимистические изменения остаются в
TanStack Vue Query, а Pinia хранит только UI-состояние. Фильтры находятся в URL, поэтому переживают
перезагрузку и корректно работают с историей браузера. Одна Zod-схема используется и формой, и API,
чтобы клиентская и серверная валидация не расходились. Мутации обновляют интерфейс оптимистично, но
имеют точечный rollback и защиту от параллельных действий.

### Разделение состояния

Данные меню являются серверным состоянием. Их загрузка, кэширование, инвалидация и оптимистичное
обновление находятся в TanStack Vue Query.

Pinia хранит только состояние интерфейса: выбранную позицию, открытие панели и toast. Серверные данные
не дублируются в store, поэтому между двумя источниками состояния не возникает рассинхронизации.

### Фильтры

Фильтры хранятся в URL, например:

```text
/?shop=bar&status=stopped
```

Значения из URL проходят runtime-проверку. Неизвестное значение не попадает в API-запрос и заменяется
на `null`.

### Справочники

Цеха и причины стопа описаны один раз в `shared/constants/menu.ts`. Из этих же опций выводятся
TypeScript-типы, строятся select-элементы, проверяются query-параметры и берутся подписи для таблицы.
Это исключает разные формулировки одной причины в форме и списке.

### Оптимистичное обновление

Перед мутацией сохраняются изменяемая позиция и её индекс. Позиция обновляется в кэше сразу, а если
после изменения она больше не соответствует активному фильтру, она сразу исчезает из текущего списка.
При ошибке восстанавливается только конкретная позиция, поэтому rollback одной операции не затирает
другие изменения. На время мутации повторные действия блокируются, а после завершения инвалидируются
запросы меню для синхронизации с сервером.

## Поведение формы и доступность

При сохранении панель остаётся открытой до ответа сервера: кнопка блокируется и показывает индикатор
«Сохраняем...», при этом строка меню меняется оптимистично сразу. При ошибке данные откатываются, toast
показывает сообщение сервера, а введённые значения формы сохраняются для повторной отправки.

Панель имеет семантику диалога, закрывается по `Esc`, удерживает фокус внутри себя при навигации
клавишей `Tab` и после закрытия возвращает фокус на элемент, который открыл панель. Если этот элемент
исчез из-за активного фильтра, фокус переводится на заголовок страницы.

## API

### `GET /api/menu-items`

Возвращает позиции меню. Поддерживает query-параметры:

- `shop`: `kitchen`, `bar`, `pastry`;
- `status`: `available`, `stopped`.

### `POST /api/menu-items/:id/stop`

Ставит позицию в стоп или обновляет существующий стоп.

```json
{
  "reason": "equipment",
  "until": "2026-09-18T12:30:00.000Z"
}
```

Для срока до конца смены `until` должен быть равен `null`.

### `POST /api/menu-items/:id/resume`

Возвращает позицию в продажу. При остатке `0` сервер отклоняет операцию.

## Ограничение тестового API

Данные находятся в памяти процесса и сбрасываются после перезапуска dev-сервера. На Vercel состояние
также может исчезнуть после холодного старта, а разные serverless-инстансы не обязаны видеть изменения
друг друга. Это ожидаемое ограничение тестового API: в рамках задания он имитирует бэкенд без базы данных.

## Ограничение тестового API

Данные находятся в памяти процесса и не сохраняются в базе данных. Локально они сбрасываются после
перезапуска dev-сервера. На Vercel serverless-инстанс может быть пересоздан после cold start или деплоя,
а разные инстансы не обязаны разделять одну память, поэтому состояние также может сбрасываться между
запросами. Для тестового задания это ожидаемое поведение.
